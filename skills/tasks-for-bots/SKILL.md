# Track work with Ambitious Tasks

Use the installed `ambitious-tasks` binary. Run `selfcheck` at routine start and read `data.problems`; resolve a reported problem before writing tasks. `commands` lists the available operations. Read the repository README for every input shape and the meaning of estimates and schedules.

Create a task with `add` when there is a concrete outcome to track. Include a useful title and `done_when`. Link prerequisites with `depends_on` or `dep add`; never describe an unrecorded dependency as enforced. Use `get` or `list` before editing existing work. Change details with `update`, state with `status`, and prerequisites with `dep add` or `dep rm`. When a task is in the wrong list, move it with `list move` and `{id, list, idem_key}`: the task keeps its id, details and history, and the move is recorded in `history`. Never cancel a task and add it again just to change its list. `update` with `patch.list` also moves a task and suits a move made together with other edits.

Always pass an `idem_key` for a write. Choose one stable key per intended action and keep both the key and input unchanged for a retry. Use a new key for a new action. If a call fails with `E_IDEMPOTENCY`, inspect the original action instead of changing its payload under the same key. Do not repeat a timed-out write with a new key before checking whether the original succeeded.

Finish a task only after its acceptance evidence is available. Record a short status note with that evidence. A done task reopens only with `status` and `reopen:true`, targeting `todo`; do not try to bypass that rule through update or import. Reopening is a deliberate user-visible action.

Ask `next` when choosing work. Each ranked item is the full task as `board` shows it, including `assignee`, `due`, `priority`, `status` and `list`, with `null` for a value that is not set, so read those fields from the item instead of calling `get` again or parsing them out of the reasons. Relay its reasons, including any `needs approval` reason and approval label. Being ranked does not grant approval. A task is ready only when all its prerequisites are done. If a prerequisite was canceled, resolve the dependency explicitly.

Never compute task counts, ranking, critical paths, workload totals, dates or process metrics by hand. Use `counts` for how many tasks are open, stale for 7 or more days, blocked, waiting or finished in the last 7 days, and report its `asOf` time and its `list` with the numbers. Pass the list name; without one, `counts` reports the list named `default`, where tasks added without a list go. Check `exists` before reporting: when it is `false` no task has ever been in that list and the counts are `null`, so do not report zero or an empty board. Relay the `note`, which names the lists that do exist, and ask which one was meant. Use `graph`, `process metrics`, `process simulate`, `schedule suggest` and `schedule check` for the rest. Copy the time and seed from `meta` when reproducing a result. State that simulation and schedule dates are estimates under their documented assumptions.

Schedule suggestions are read-only. `schedule suggest` needs `horizon_days` and a `people` roster on every call, for example `{"horizon_days":14,"people":[{"id":"member","capacity_days_per_week":5,"windows":[{"start":"2026-01-05T09:00:00Z","end":"2026-01-09T17:00:00Z"}]}]}`. The window dates there are placeholders: each window must fall between the command time and `horizon_days` later, and windows that end before the command time or start after the horizon are ignored. Leave `windows` out for a person who is always available. The module has no command that adds people and does not store the roster; without `people` it normally has nobody to schedule and returns `NO_FEASIBLE_SLOT` for every ready task. When a violation is `NO_FEASIBLE_SLOT`, read its `reason` and `hint`: an empty roster, an assignee missing from the roster, and nobody having room within the horizon need different fixes. Pass the same people to the independent schedule checker. Explain any violations before proposing assignment changes, then use `update` for task assignees when authorized. Do not present a suggestion as a committed schedule.

Read the envelope and exit code after every command. An `ok:false` response contains a code, message and next-action hint; relay the useful information without inventing a successful result. The module works without network access or provider keys. Never place credentials or private bot files in task inputs.
